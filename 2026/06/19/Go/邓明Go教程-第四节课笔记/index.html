4.3 URL 设计风格

风格 示例 说明
非 REST POST /users/login 动词在 URL 里
REST POST /users/signup URL 代表资源，HTTP 方法代表操作
极端 REST POST /users 同一 URL，靠方法区分

我们把 HTTP 请求理解成两个部分：

  1. 动作（HTTP 方法）：GET（查）、POST（增）、PUT（改）、DELETE（删）
  2. 对象（URL 路径）： /users（用户）、/orders（订单）

用 Gin 代码 对照表格，给你翻译一下这三者的具体区别：

1. 非 REST 风格（动词在 URL 里）

特征：路径里直接带上 login、signup 这种“动作”单词。

2. REST 风格（URL 代表资源，方法代表操作）

特征：路径里只写名词（资源是什么），用 HTTP 的 GET/POST 等动词 来决定“要干嘛”。

优势：URL 非常干净，只有 /users 和 /users/123。别人一看就知道你在操作“用户”，具体的动作（查、增、改）完全由 HTTP 方法决定。

3. 极端 REST 风格（极其抽象，完全靠方法区分）

特征：不但在路径里不写动词，甚至连路径都不区分了。所有关于用户的操作，统统走同一个路径 /users。
Gin 代码：

优势：这也最符合《RESTful API 纯洁派》的理论，把 Web 服务想象成对数据库表做纯粹的 CRUD（增删改查）。
缺点：有点“太极端”了。比如你给用户做“登录”操作，用纯粹 REST 很难通过简单的 HTTP 方法表达出来，所以像登录、注册这种带有业务逻辑的操作，大家通常还是会用折中方案（比如 POST /users/login）。

开发时的实用建议：
看上面表格里的例子，它把“登录”写在 REST 里，其实是不对的。真正的 REST 是不允许路径里带 login 这种动词的。
所以实际工作里，我们通常是**“核心业务用 REST（比如查用户、改用户），非纯粹 CRUD 的动作用非 REST（比如登录、支付）”**，两者混合使用，怎么舒服怎么来。

结合代码：
server.GET("/hello", func...)
这其实就是标准 REST 风格！因为 GET 是动作，/hello 是资源。你在告诉自己：“我要用 GET 方式，去获取 /hello 这个资源（或者说接口）的数据。” 所以你用浏览器访问它，完全没问题。

4.5 接收请求：Bind 方法

为什么 Bind 必须传指针？ 值传递问题——如果传值，Bind 修改的是副本，原结构体不会变。

Bind 怎么区分 JSON / Form / XML？ 根据请求头 Content-Type 自动判断：

  • application/json → JSON 绑定
  • application/x-www-form-urlencoded → Form 绑定

用 Postman 测试时：Header 里加上 Content-Type: application/json，Body 选 raw → JSON。

五、参数校验

5.1 核心原则：不能信任前端

不管前端有没有校验，后端一定要校验。 通过 Postman 可以直接绕开前端，所以前端的校验只是用户体验优化，安全靠后端。

5.2 校验内容

以注册为例：

  • 邮箱：格式合法（正则匹配）
  • 密码：不少于 8 位，必须包含数字和特殊字符
  • 确认密码：和密码一致

六、关键概念速查

概念 说明
*gin.Engine 逻辑服务器，可启动多个监听不同端口
*gin.Context 一次请求的上下文，处理输入和输出
gin.HandlerFunc func(*gin.Context) 的衍生类型
ctx.Bind(&req) 根据 Content-Type 自动绑定请求数据
ctx.Param("name") 取路径参数
Route Group 路由分组，自动拼接前缀
internal/ 项目内部私有包，外部模块无法引用
Content-Type 告诉后端请求数据格式（JSON/Form/XML）
