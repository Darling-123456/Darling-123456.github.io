核心内容：项目分层落地（handler-service-repository-dao）、bcrypt 密码加密、Cookie/Session 机制、登录校验中间件、用户注册完整链路
前置知识：Gin 路由与中间件、GORM 增删改查、Docker Compose

一、项目分层架构落地

0.改造代码

1.1 为什么要分层？

这次要解决的第一个问题是：数据库代码放在哪？

如果所有代码都堆在一个文件里，很快会变成一坨「意大利面条」。分层之后，每一层只干一件事，修改一处不影响其他地方。

1.2 四层架构

逐层说明：

层 职责 类比
handler 接收 HTTP 请求，调用 service，返回 HTTP 响应 前台接待
service 核心业务逻辑，组合各种 repository 业务经理
repository 「存数据」的抽象接口，不管存到哪（DB/缓存/文件/RPC） 仓储接口
dao 真正操作数据库的代码（GORM 在这里） 仓库管理员

核心规则：上层可以调下层，下层不能调上层。handler 可以用 service 的类型，但 service 不能用 handler 的类型。

1.3 domain：业务领域对象

这个 User 是业务层面的概念——和注册表单对应，但和数据库表可能不一样。

1.4 dao：数据库模型

为什么 dao.User 和 domain.User 是分开的？

domain.User dao.User
含义 业务上的用户 数据库里的用户
字段 Email, Password 加上 ID, Ctime, Utime
是否和数据库耦合 否 是

随着业务复杂，两者差异会越来越大。比如数据库里存的是 int64 毫秒数，业务里想用 time.Time，转换就在 dao ↔ domain 之间完成。

二、密码加密

2.1 为什么必须加密？

  • 数据库泄露 = 所有用户明文密码泄露
  • 用户往往在多个网站用同一个密码——一个站炸了就全炸了
  • 防外鬼（黑客），也防内鬼（同事直接看数据库）

2.2 加密放在哪一层？

四种选项各有道理：

位置 理由 缺点
service 加密是业务概念，产品经理要求「密码必须加密」 -
repository 加密是存储概念——存到仓库的东西就应该加密 -
dao 只有数据库才需要加密，放缓存不加密 绕开 dao 访问 repository 会拿到明文
domain 密码是 User 自己的事，User 自己负责加密 u.Encrypt() 这种写法比较别扭

放在 service 层——代码最直观，最容易读懂。选择不同位置会影响后续接口设计，但没有标准答案。

2.3 加密算法选择：bcrypt

bcrypt 的特点：

  • 相同的密码每次加密结果不同（内置随机盐）
  • 不可逆——无法从密文解密出明文
  • 天然抗彩虹表攻击
  • DefaultCost 控制计算强度（值越大越慢，也越难暴力破解）

2.4 时间字段用毫秒数而非 time.Time

原因：time.Time 带时区信息，应用层和数据库层各有时区概念，双重时区极易出错。直接用毫秒数，简单粗暴不出错。

六、HTTP 无状态 & Cookie & Session

6.1 HTTP 是无状态的

你登录成功后，下次再发请求，服务器完全不记得你是谁。HTTP 协议本身不保存任何客户端状态。

6.2 Cookie：浏览器端的键值对

字段 含义
Name Cookie 的名字
Value Cookie 的值
Path 作用路径。设 / 表示整站可用；设 /admin 只在 /admin 下发送
Domain 作用域名。设 example.com 则 www.example.com 和 api.example.com 都能用。不设默认当前域名
Expires 过期时间（绝对时间）。设过去的时间就是删除
MaxAge 存活秒数（相对时间）。0 = 删除，负数 = 会话级（浏览器关了就没）。和 Expires 同时设的话 MaxAge 优先
Secure true 时只在 HTTPS 下发送，HTTP 不发送
HttpOnly true 时 JS 的 document.cookie 读不到，只能 HTTP 传输。防 XSS 偷 cookie
SameSite Lax / Strict / None，防 CSRF。Strict 最严（任何跨站都不发），Lax 允许点击链接时带，None 不限制（必须配合 Secure: true）

Gin 里设置 Cookie：

最后两个 Secure、HttpOnly 生产环境建议都设 true。

Cookie 的安全属性：

属性 含义 生产环境
HttpOnly JS 脚本读不到 必须设为 true
Secure 只在 HTTPS 下传输 必须设为 true
SameSite 不允许跨站携带 按需设置
Domain 生效域名范围 最小化原则
Path 生效路径 最小化原则
Expires / MaxAge 过期时间 按需设置

Cookie 最大的问题：存在浏览器端，用户可以改，木马可以偷。不适合存敏感数据。

6.3 Session：服务端存储

  • Session 数据存在服务端（内存/Redis/数据库），用户看不到

  • 浏览器只拿一个 sessionID（存在 Cookie 里）

  • Session 是认 ID 不认人的——拿到 sessionID 就等于拿到身份

7.4 分组注册——区分需要登录和不需要登录的路由

  • 免登录接口： server.POST("/users/signup", ...) 和 server.POST("/users/login", ...) 直接注册在主引擎上，完全不经过任何身份验证中间件。用户不用登录就能注册和登录。
  • 受保护接口： authGroup := server.Group("/users") 创建了一个专门的路由组（这个组的根路径是 /users）。
  • 挂载中间件： 通过 authGroup.Use(...) 挂载了登录校验中间件。重点在于 IgnorePaths("/users/signup", "/users/login")。这通常是个自定义的中间件功能，它意味着：
    • 虽然这个分组里的所有路由（如 /users/profile）都会触发中间件进行校验。
    • 但是，如果请求的路径是 /users/signup 和 /users/login，中间件会特殊处理，直接“放行”，不做登录校验。这被业界俗称为**“白名单”或“放行路径”**。

或者更简洁：直接分两个 group，一个不加中间件，一个加。

直接分两个 group是什么意思？

这是业界常见的两种方案，面试时也是高频考点：

  • 方案一（代码中展示的方案）：用“黑名单/白名单”机制（IgnoredPaths）。

    • 特点：所有路由都挂在同一个组下，依赖中间件内部去判断“哪些路径不需要鉴权”。
    • 优劣势：代码紧凑，只有一个路由组。但缺点是逻辑耦合，如果放行路径越来越多，中间件内部会变得比较臃肿，容易出错。

  • 方案二（注释中提到的方案）：物理分离。

    • 特点：把路由分成两个完全独立的路由组（物理隔离）。

      go

    • 优劣势：代码职责分离极其清晰。完全不需要在中间件里做 if/else 的路径放行判断，性能略微提升，可维护性极佳。

八、核心概念速查

概念 一句话解释
分层架构 handler → service → repository → dao，上层调下层
domain 对象 业务意义上的实体，不关心怎么存
dao 对象 直接对应数据库表结构
bcrypt 不可逆加密，每次加密结果不同，天然抗彩虹表
HTTP 无状态 服务器不记得你上次是谁
Cookie 浏览器端键值对，不安全但方便
Session 服务端存数据，浏览器只拿 ID
HttpOnly + Secure Cookie 安全双保险，生产必开
唯一索引 数据库级别防重复的最后防线
Builder 模式 方便后续给中间件加扩展参数
