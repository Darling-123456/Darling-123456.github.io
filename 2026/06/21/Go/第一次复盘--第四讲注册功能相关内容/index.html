GO学习笔记 | 第四讲注册功能相关内容复盘

代码仓库地址：Darling-123456/go_learning: go学习过程记录

1. Engine vs Context

Engine：gin.Default() 返回一个 *gin.Engine，它是整个 HTTP 服务器的抽象。一个 Engine = 一个逻辑服务器，绑定一个端口。可以启动多个 Engine 监听不同端口（比如 :8080 给用户，:8081 给后台管理）。

Context：*gin.Context 代表一次请求。每个 HTTP 请求到达时，Gin 创建一个 Context，把 Request（输入）和 Writer（输出）都包进去，然后传给路由处理函数。请求结束，Context 销毁。

一句话：Engine 是长生命周期（进程级），Context 是短生命周期（一次请求）。

2. 参数路由 vs 通配路由

核心区别：:name 是单段匹配，*filepath 是贪婪匹配到末尾。

3. ctx.Bind(&req) — 为什么传指针？JSON / Form 怎么自动识别？

为什么传指针：Bind 需要修改 req 的字段值。Go 的参数传递是值拷贝，传 req 进去的话，Bind 改的是副本，外面的 req 不变。传 &req，Bind 通过指针直接改原变量。和你 C++ 里 void fill(User* u) 要传指针是一个道理。

JSON / Form 自动识别：Bind 读的是 ctx.Request.Header 里的 Content-Type：

  • Content-Type: application/json → 用 JSON 解析器，填到 struct tag 是 json:"xxx" 的字段
  • Content-Type: application/x-www-form-urlencoded → 用 Form 解析器，填到 struct tag 是 form:"xxx" 的字段

前端发请求时自己设了 Content-Type，Gin 就按对应的解析器走。

4. 正则预编译 — 为什么在 NewUserHandler 里做？

正则的编译（把字符串 "^[a-zA-Z0-9...]$" 转成状态机）是一个重操作。如果放在 SignUp 里每次请求都 MustCompile，每次注册都重新编译一遍，白白浪费 CPU。在 NewUserHandler 里调用一次，之后所有请求复用编译好的对象。

NewUserHandler 在 main.go 里只调用一次（进程启动时），所以编译也只发生一次。

5. CORS — 这是什么问题？

场景：前端跑在 http://localhost:3000，后端跑在 http://localhost:8080。浏览器发现 JS 代码（来自 :3000）要去请求 :8080 的接口——域名一样但端口不同，这是”跨域”。

浏览器默认会拦截这个请求（除非后端明确说”我允许”）。

CORS 机制：后端在响应头里加上 Access-Control-Allow-Origin: http://localhost:3000，告诉浏览器”这个人我认识，放行”。cors.New() 中间件就是自动帮你加这些头。上面的代码里 AllowOrigins: []string{"http://localhost:3000"} 就是在配白名单。

关键：这是浏览器的安全策略，不是后端的安全策略。Postman / curl 不经过浏览器，所以不受 CORS 限制。

6. internal/ 目录

Go 编译器的硬约束：internal/ 下的包，只能被它的直接父级目录树导入。

就是你项目内部的私有代码，防止外部依赖无意中引用你的内部实现细节。

7. 整体架构链路

链路逻辑：main.go 负责启动和组装，UserHandler 负责定义路由和处理逻辑。 这是 Go 里最常见的分层模式——main 做依赖注入（把 Engine 传给 Handler），Handler 做路由注册+业务处理。

8. gin.Default() 自带 Logger 和 Recovery

Default() 不是空 Engine。它内部自动挂了两层中间件：

  • Logger：每次请求打印一行日志（方法、路径、状态码、耗时）——你启动服务时终端刷出来的那些就是它。
  • Recovery：处理函数里 panic 了不会让整个服务挂掉，会返回 500 并恢复。

对比 gin.New() 是裸 Engine，什么中间件都没有。之所以你用的 Default() 是标配，因为 Logger + Recovery 是所有 Web 服务都需要的。

9. ctx.Bind 失败时自动写 400 响应

这很隐蔽但重要：

Bind 失败时已经自动往 ResponseWriter 里写了状态码 400 并设置了 Content-Type: text/plain。你在后面再 ctx.String(400, ...) 其实是追加了一段文本，状态码倒是没冲突。

Gin 还有一个 ctx.ShouldBind(&req) —— 它只绑定不写响应，失败时返回 error，由你自己决定怎么处理。以后如果你不想用 Bind 默认的 400 行为，就用 ShouldBind。

10. server.Run(":8080") 会阻塞当前 goroutine

Run 内部是 http.ListenAndServe，一个无限循环 accept 连接。这就是为什么你笔记里要启两个 Engine 时必须用 goroutine：

没有 go 的话第一个 Run 就卡住了，第二个根本执行不到。

11. 中间件的本质：洋葱模型

server.Use(cors.New(...)) 这是什么？中间件不是 Gin 特有的概念：

server.Use() 把中间件串成一个链。你在 main.go 里 Use(cors.New(...)) 写在路由注册之前，意味着所有路由都会经过 CORS 中间件。后面课程里你会接触更多中间件——JWT 校验、限流、链路追踪——都是这个 Use 模式。

12. Go modules：import 路径 ≠ 文件路径

你笔记里 import 了：

这个路径的前缀 go_learning 来自 go.mod：

Go 的 import 路径是 module 路径 + 目录相对路径，不是磁盘绝对路径。go_learning 只是一个名字，和你磁盘上的 C:\Users\... 没有关系。go.mod 里的 module 行定义了整个项目的命名空间。

13. 响应写完之后记得 return

写 ctx.String() 不会中断函数执行。忘记 return 的话代码会继续往下走，比如校验失败后继续执行数据库操作。你笔记里的代码每处分支都写了 return，这是对的。

补充：结构体标签（Struct Tag）

学习第二周第一节课即注册功能的时候不太会的内容

一、 什么是结构体标签？

定义：

在 Go 结构体字段声明的后面，使用**反引号（`）**包裹的键值对字符串。
**格式：**`key1:”value1” key2:”value2”` （如果有多个标签，用空格隔开）。

作用：它本身不参与代码逻辑，也不影响内存结构。它的真正用途是向外部包（如 Gin、JSON 库、ORM 框架）提供关于该字段的元数据（配置信息）。

二、 为什么用反引号 ` 而不是双引号 “ ？

因为标签里面的配置经常需要写双引号（比如 json:"name"）。如果用双引号包裹外部，里面又要用转义字符 \ 去写双引号，代码会非常恶心。
反引号内是原始字符串，可以直接写 "，极大提高代码可读性。

三、 实战：最常用的 3 类标签（以 Gin 框架为例）

1. json 标签 —— 处理 JSON 数据

用于 encoding/json 标准库或 Gin 的 c.ShouldBindJSON，解决 Go 大写变量名和前端小写 JSON 字段名不匹配的问题。

2. form 标签 —— 处理表单数据

用于处理 HTTP POST 请求中的 application/x-www-form-urlencoded（普通表单）或 URL 查询参数。

3. binding 标签 —— 数据校验（Gin 专属，极其重要）

用于 Gin 框架，在绑定数据的同时自动校验数据是否符合规则。如果不符合，Gin 会直接返回错误信息。

四、 高级用法：自定义标签与反射（底层原理）

很多新手以为标签只能用来搞 JSON 和 校验，其实任何包都可以通过 Go 的反射机制去读取标签，从而做自定义逻辑。

五、 新手 3 大“踩坑”必看总结

  1. ❌ 字段首字母不大写：

    后果：Gin 绑定、JSON 解析全部失效。因为 Go 的反射机制无法访问私有（小写）字段。

  2. ❌ 标签拼写错误：
    binding:"requried"（单词拼错）或者 json:"emial"。后果：通常不报错，但功能无法生效。

  3. ❌ 前后端命名不一致：
    前端传的是 confirmPassword，后端标签写的是 json:"ConfirmPassword"。后果：Go 接收到的 ConfirmPassword 字段永远是空字符串。
